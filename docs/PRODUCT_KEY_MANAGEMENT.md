# 관리자 제품 키·이력 관리

2026-11-19. 여기서 제품 키는 Office·한컴 라이선스 값이며 PC BIOS S/N과 별개다.

## 화면·프로그램 구조 확인

현재 기존 운영 이미지는 v1 화면으로 /admin/apps와 /admin/tools가 없었다. 별도 v2의8001/9443에는 해당 화면이 있다. Git 브랜치 이름과 실행 중인 이미지의 기능은 같지 않다. 이번에는 기존 운영 이미지에 제품 키 기능만 추가한다. 기존 운영 주소의 `/admin` → **제품 키·이력 관리** 또는 `/admin/licenses`로 진입한다.

MVC 구성:

- Model: Server/models/license_history.py — 제품 키 암호화, 변경·정상 확인·복구·작업 전달 이력.
- Controller: Server/controllers/licenses.py — 기존 관리자 세션/역할 검증, 고정 프로그램 ID, 형식 검증, 인증된 에이전트 동기화.
- View: Server/views/licenses.html 및 licenses.js — 마스킹된 목록, 버전/메모, 저장·적용·정상 확인·문제 표시·복구.
- 기존 DeploymentMedia는 관리 키가 있으면 ZIP의 키 파일 내용만 DB 값으로 구성한다. 원본 media 디렉터리와 기존 키 파일은 변경하지 않는다.
- 최신 PrepareAgentMedia/LicenseKeys는 원본 캐시가 있어도 매 셋업 시작 때 키만 동기화한다. 작업 중인 키 변경은 서버에서 차단한다.

## 사용 순서

1. PC 관리에서 관리자 로그인 후 제품 키·이력 관리로 이동한다.
2. 프로그램, 버전·관리 이름, 제품 키, 메모를 입력해 **검증 전 이력으로 저장**한다. 키 원문은 다시 표시하지 않는다.
3. 대상 이력의 **이 값 적용**을 누른다. 저장만으로 현재 값은 바뀌지 않는다.
4. 테스트 PC에서 설치·인증을 확인한 뒤 **정상 확인**을 누른다. 형식 검사나 종료 코드만으로 자동 정상 판정하지 않는다.
5. 문제가 있으면 **문제 표시** 후 이전 정상 이력의 **이전 정상 값으로 복구**를 누른다. 문제로 표시된 활성 키는 새 셋업 준비를 차단한다.

Office 키는 5문자씩 5개 그룹 형식이며, 한컴은 영문/숫자·하이픈 형식을 사용한다. 형식 통과가 라이선스 유효성이나 제품 버전 호환성을 뜻하지 않는다. 제품 키를 이름·메모에 적지 않는다.

정상 이력 최소 3개를 보존하는 요구에 맞춰 현재는 **이력 전체를 삭제 없이 보존**한다. 최초에는 정상 이력이3개 없을 수 있으며 실제 확인 없이 정상값을 만들어내지 않는다. 기존 파일은 ‘기존 서버 파일 / 검증 전’으로 최초 한 번 보관하고 현재 값으로 유지한다. 새 이력은 UUID로 식별하며 기존 값을 덮어쓰지 않는다.

## 적용 범위와 기존 PC

- 실행 중·대기·중단 상태의 전체 셋업 작업이 있으면 적용·복구·정상/문제 상태 변경을409로 막는다. 새 후보 저장은 가능하다.
- 키 변경은 다음 셋업에서 사용할 키 파일을 바꾼다. 이미 설치된 Office의 제품 키·정품 인증을 직접 변경하는 기능이 아니다.
- 기존 PC는 같은 서버의 HTTPS에서 최신 ZIP을 새로 받아 InstallAgent.bat을 관리자 권한으로 **한 번** 실행해 에이전트를 갱신해야 한다. 진행 작업/ActiveJob이 있으면 먼저 확인하며 임의 삭제하지 않는다. 이후 웹에서 키만 바꾸는 경우 에이전트를 매번 재설치할 필요는 없다.
- 에이전트 키 요청 때 실행 중인 해당 PC 작업 ID와 키 이력을 기록한다. UI에는 당시 전달한 키 이력과 현재 작업 결과가 연결된다. 전달 기록은 실제 정품 인증 증거가 아니다.
- 구버전 에이전트는 동기화 기능이 없으므로 캐시된 키를 계속 쓸 수 있다. 새 에이전트가 구버전 서버를 만나면404에서 기존 파일 방식으로 동작한다. 인증·네트워크 오류는 오래된 키로 몰래 진행하지 않고 LICENSE_SYNC_FAILED로 중단한다.

## 보관·백업

DB 테이블: license_revisions, license_active, license_audit, license_job_revisions.

제품 키 원문은 Fernet으로 암호화해 DB에 저장한다. 복호화 키는 DB와 같은 영속 디렉터리의 `license-vault/master.key`에600, 디렉터리는700으로 보관한다. 관리자 목록·감사 이력·공개 ZIP·공개 config API에는 원문을 넣지 않는다. 승인된 에이전트는 설치 원본 다운로드와 같은 권한으로 필요한 키를 받는다. 현재 단일 관리자 인증 기반으로 작업자 개인 식별은 제공하지 않는다.

**DB와 master.key를 함께 백업**해야 한다. DB에 이력이 있는데 master.key가 없으면 새 키를 생성하지 않고 중단한다. 키 파일과 DB를 동시에 잃으면 이력만으로 원문을 복구할 수 없다. 기존 media 원본 키 파일은 별도 보존하되 이후 관리 이력의 최신값과 같다고 가정하지 않는다.

이번 배포의 프로젝트별 기록은 `/home/jobchoi/web-server/<프로젝트>/backups/20261119-license-dashboard/`에 둔다. recovery.tar.gz는 이전 Compose/설정/DB, encrypted-recovery.tar.gz는 배포 후 DB/master.key 복구본이다. WSL Git 제외 downloads/operation-backups/20261119-license에도 보관하고 해시·SQLite·복호화를 검사한다. 원시 복구본과 인증·제품 키는 Git/블로그에 올리지 않는다.

이전 이미지로 서버를 되돌리면 이 기능을 모르는 서버는 원본 media 키를 사용한다. 실제 키 변경 이후에는 이 차이를 확인한 뒤 되돌린다. 이번 배포에서는 실제 제품 키를 새 값으로 바꾸거나 정상으로 표시하지 않는다.

## 다음 범위

Office·한컴 설치 원본 ZIP 업로드/버전 보존, 설치 옵션·환경 구성 프로필, 설치 원본 버전 전환은 후속이다. 제품 키 복구가 설치 파일이나 PC 프로그램을 이전 버전으로 되돌리는 것은 아니다. 일반 MSI 앱의 기존 v2 카탈로그 버전 관리와도 구분한다. 다음에는 원본 패키지 해시·불변 버전·검증 상태·키 revision·옵션을 하나의 배포 구성으로 고정하는 설계를 적용한다.

## 검증

모델/API는 암호화·원본 보존·정상 이력 3개 이상·복구·진행 작업 차단·작업 이력 연결·역할 차단을 확인한다. Chromium은 저장·적용·3개 정상 이력·문제 표시·복구를 검증한다. Windows PowerShell은 인증된 키 갱신·캐시 원본 재사용·쓰기 전 검증·임시 파일 정리와 기존 준비 함수를 모의 검증한다. 실제 PC 설치/라이선스 인증은 별도 현장 확인이다. 실행 결과와 Pi 적용 상태는 WORK_HISTORY의 최신 기록을 따른다.
