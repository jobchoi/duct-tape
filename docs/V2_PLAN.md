# v2 기획 초안

작성: 2026-10-08. 상태: 의견 제안, 구현 범위 미확정.
사용자 요청에 따라 기능 구현을 잠시 멈추고 운영 조건과 실패 복구를 기획한다.
현재 코드는 v1 현장 시험 기준선으로 취급한다. 2026-10-14 한컴 설치기 성공 반환 후 종료 상태/UTF8 처리를 수정했다. 최신 에이전트의 관리자 요청부터 완료 보고까지 현장 검증은 아직 없으며 실패 후 재요청 무반응도 남아 있다. 정식 릴리스는 [다음 작업 계획](NEXT_WORK_PLAN.md)의 검증 뒤 진행한다.

## 목표와 우선순위

2026-10-16 구현 업데이트: MSI 어댑터 규약의 UI 초안 등록/공개, 클라이언트 선택 설치, 버전 고정 패키지·클라이언트 캐시, PC별 앱 결과와 등록 필요 표시를 feature/v2-mdm-ui에 추가했다. [구현/검증 범위](V2_APPLICATIONS.md)를 참고한다. Argos 실제 Windows 설치와 공식 무인 등록, 기존 전체 셋업의 전송/보고 문제는 해결됐다고 간주하지 않는다.

2026-10-16: 사용자 요청으로 v1을 main/v1.0.0-rc.1에 보존하고 feature/v2-mdm-ui에서 v2를 착수한다. 최초 확장 목표는 MDM 설치와 UI 모듈 관리이며 제품 정보는 질문 중이다. [MDM 착수 계획](V2_MDM_START.md)에 구현 전 확인 사항과 상태 모델을 기록했다. 아래 기존 과제는 폐기하지 않고 함께 범위를 조정한다.

목표는 여러 Windows PC의 환경 셋업을 시작하고, 결과를 검증하며, 실패 이유와 안전한 다음 조치를 관리자가 확인하는 것이다.

1. P0: 현재 한컴 실패 진단, 앱별 설치 로그 수집·비밀값 제거, 종료 코드와 실패 단계 표시, 설치 후 검증.
2. P0: 중단·재부팅·통신 단절 상태 구분, 체크포인트와 선택적 재시도. 실패 시 전체 제거/설치를 처음부터 반복하지 않는다.
3. P1: Office 설치 방식별 제거 전략과 제거 후 검증, 보존할 Project/Visio 정책.
4. P1: 버전별 배포 패키지 캐시·해시 검증·재사용, 다운로드 동시 수 제한, 병렬 실측.
5. P1: 기관 내부망/외부망별 운영 문서와 Raspberry Pi 4 실장 검증.

2026-10-14 요구 추가: 관리자 UI에서 앱 모듈 등록/검사/공개, 클라이언트 UI에서 앱 선택 설치를 v2 범위로 기획한다. 기존 안정화 방향은 유지하며 규약과 실행 패키지 전달을 공통 기반으로 설계한다. 상세 순서와 MVC 책임은 [다음 작업 계획](NEXT_WORK_PLAN.md)에 정리한다. 복잡한 선택 옵션, 다중 서버·고가용성은 후속 범위다.

## 운영 형태

| 환경 | 제안 | 선행 조건 |
| --- | --- | --- |
| 같은 기관 내부망 | 내부 서버 주소로 Windows 에이전트 접속 | 기관 승인, 주소/DNS, HTTPS 인증서와 접근 권한 |
| 완전 폐쇄망 | 설치 원본과 의존성을 사전 반입 | Office 전체 오프라인 원본, 제품별 인증 방식 확인 |
| 외부망/원격 | 승인된 VPN 또는 Tailscale을 연결 수단으로 사용 | 기관 네트워크 정책과 요금 조건 확인 |

Tailscale은 선택 가능한 연결 수단이다. 프로그램의 서버 주소와 인증 구조를 특정 VPN에 종속시키지 않는다. 망 분리 정책을 우회하거나 내부·외부망을 임의로 연결하지 않는다. GitHub Pages는 정적 문서 용도이며 실행 서버 역할을 대신하지 않는다.

Pi 4 + 유선 LAN + SSD를 우선 후보로 제안한다. Pi 3는 보조/소규모 시험 후보다. RAM, Pi 3 세부 모델, SSD 유무는 미확인이다. ARM64 의존성 설치와 실제 전송 성능은 별도 검증해야 한다. 임시 ZIP과 DB는 충분한 로컬 디스크에 둔다.

2026-10-14 사용자 답변: 서버 구축은 Pi 4 → Pi 5 방향으로 계획하며, 병렬 대수와 폐쇄망 지원은 후순위로 진행한다. 클라이언트는 Windows 재설치 후 현장 검증한다. Pi 5 자원과 이전 시점은 별도 확정한다.

## 병렬 실행

현재 서로 다른 PC는 설치를 병렬 실행할 수 있고, 동일 PC의 활성 작업은 하나로 제한한다. 설치 CPU 부하는 각 PC가 부담한다. 서버는 다운로드와 상태 보고를 처리한다.
현재 요청마다 큰 임시 ZIP을 만들므로 Pi의 저장 공간·I/O·회선이 병목 후보다. 지원 대수는 아직 실측되지 않았다.

제안: 원본 버전별 패키지 캐시, 클라이언트 캐시, 무결성 검증, 전송 동시 수 제한을 도입한다. 다운로드 동시 수와 설치 동시 수를 분리한다. 최초 1→3→목표 대수로 확대하며 전송 시간, 디스크 최대 사용량, 관리자 응답 시간, 성공률을 기록한다. 초기 2~3개 동시 다운로드는 시험 설정 제안이며 보장 수치가 아니다.

## Office 제거

현재 모듈 03은 ODT /configure remove.xml을 자동 실행한다. 현재 XML은 Remove All="TRUE"이고 RemoveMSI가 없다. 모든 설치 형태와 손상 상태를 처리한다고 볼 수 없으며 Project/Visio 보존 정책도 필요하다.

제안 흐름: 설치 제품/버전/방식 조사 → 제거 대상 결정 → Click-to-Run은 ODT, MSI는 해당 공식 제거 방식 → 잔여/손상 상태는 공식 Get Help 명령줄 제거 도구 적용 가능성 검토 → 재부팅 필요 여부 기록 → 제거 검증 → 새 설치.
Get Help 명령줄 도구도 실행 중 Office나 복수 버전 등의 조건에서 중단할 수 있다. 모든 사례의 무인 처리를 보장하지 않는다. 대화형 제거 도구의 버튼 자동 클릭, 임의 레지스트리 삭제는 기본 전략으로 삼지 않는다.

## 실패와 복구

manage.sh 로그는 서버 로그이므로 Windows 설치기의 상세 원인을 보여주지 못할 수 있다. VC++ 1638과 완료 후 종료 코드 오판 대응은 [한컴 복구 문서](HANCOM_RUNTIME_RECOVERY.md)에 기록했다. 실제 설치/인증 검증과 다른 실패의 진단 체계는 여전히 필요하다.
현재 에이전트 로그 후보: C:\ProgramData\DuctTapeAgent\logs\<작업ID>.out.log, .err.log, .progress.jsonl. 모듈 Deployment.log는 실행 계정의 TEMP 아래 duct-tape에 저장된다. SYSTEM 계정 TEMP와 대화형 사용자 TEMP가 다를 수 있다.

제안 데이터: 작업/PC/앱 ID, 패키지 버전, 단계, 시도 횟수, 설치기 종료 코드, 마지막 성공 체크포인트, 재부팅 필요, 설치 검증 및 인증 결과. 설치 성공과 라이선스 인증 성공을 분리한다.
설치기 상세 로그는 키·명령줄 비밀값을 제거한 진단 묶음으로 수집하고 관리자에게만 제공한다. 서버 접속 키와 제품 키 원문을 수집하지 않는다.

네트워크 일시 실패는 제한 재시도, 다른 MSI 작업 중이면 대기, 원인 미확정 설치 실패는 중단 후 진단한다. 재시도 전에 실제 설치 상태를 다시 탐지한다. 제거 후 실패는 제거 이전 상태로 자동 복원되었다고 표시하지 않는다. 재부팅 후에는 검증된 체크포인트와 서버 작업을 대조해 이어간다. 다른 설치기의 msiexec 등을 프로세스 이름만으로 종료하지 않는다.

## 수용 시험 제안

- 깨끗한 Windows PC에서 Office/한컴 설치 후 실제 제품·버전 검증.
- Office 2021 C2R, 구형 MSI, 손상 설치, 이미 정상 설치된 PC에서 제거/건너뛰기 결과 검증.
- Project/Visio 보존, 앱 실행 중 제거, 다른 MSI 실행, 재부팅 필요 상태.
- 다운로드 단절·손상, 서버 중단, 에이전트 재시작, 제거 후 설치 실패, 같은 PC 중복 요청.
- 여러 PC 병렬 실행 중 작업/로그 혼선 없음, 설치 성공과 인증 실패 구분, 키가 화면·진단 묶음에 노출되지 않음.
- Pi 4에서 목표 대수 시험; 내부망 및 사전 반입 원본만 사용하는 폐쇄망 시험.

## 미확정 사항

동시 목표 대수, 완전 폐쇄망 여부, Pi 4 RAM/SSD, 실제 Office 제거 도구 이름, 제품 인증 방식, 현재 한컴 작업 ID와 비밀값을 제거한 오류 코드/로그가 필요하다. 이 문서는 새 기능 구현 승인이나 성능 보장을 뜻하지 않는다.

## 2026-10-15 현장 피드백: 다음 기획 논의 후보

사용자 요청에 따라 메모만 남긴다. 아래 후보의 채택·우선순위·구현 범위는 추후 v2 기획 논의에서 정하며 이번에는 기능을 변경하지 않는다.

- Windows 업데이트/재부팅이 잦은 초기화 PC: 에이전트 재시작과 작업 이어가기를 구분한다. 현재 진행 중 작업은 재시작 시 interrupted로 보고하고 자동 재실행하지 않는다. 완료 후 미전송 결과는 재전송한다. 다운로드 이어받기 및 설치 체크포인트 복구는 미지원이다.
- 후보: 원본 버전/해시 고정, 다운로드 이어받기·무결성 검사, 재부팅 전후 설치 상태 재탐지, 재부팅 필요 상태 표시, 안전한 단계별 재시도. Office 제거 등 파괴적 단계를 중복 실행하지 않는 기준이 필요하다.
- 두 탭북 동시 다운로드: 같은 약 1.15GB 원본에서 첫 작업 약 714MB(62.2%), 두 번째 약 2.1MB(0.18%)였고 양쪽 모두 running/진행 보고 중이었다. 단순한 전역 큐 대기로 확인된 것은 아니다. 두 번째는 약 42초에 32KB 증가했다.
- 측정 당시 컨테이너 CPU 1.43%였으나 전송 지연의 원인은 미확정이다. Funnel·기관망·Wi-Fi·클라이언트·저장장치 등을 구분해 비교해야 한다. 스위치나 Pi 성능 부족으로 단정하지 않는다.
- 배포 후보: 요청마다 ZIP 생성하는 현재 방식의 캐시/버전 고정, 동시 전송 제어, HTTP Range 분할·이어받기, 내부망 배포, 노트북을 이용한 파일 배포 역할 분리. 캐시와 분할 전송만으로 회선 총대역폭 한계가 해결되지는 않는다.
- 관리자 UI 후보: 전체 대기/실행/성공/실패 대수와 PC별 단계·전송량·속도·최근 응답·중단 이유를 목록에 표시하고 선택 PC의 상세 로그로 연결한다. 현재 진행 내역 하나만 보이는 현상은 선택 UI인지 갱신 결함인지 미확정이다.
- 다음 논의에서는 기본 안정화, 현장 다운로드, 재부팅 복구, 모듈 등록/선택 설치 UI를 함께 검토해 범위를 추린다. Windows 업데이트 제어 기능을 구현하기로 결정한 것은 아니다.
