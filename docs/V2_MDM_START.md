# v2 착수: MDM 우선 설치와 앱 관리 UI

작성: 2026-10-16. 브랜치: feature/v2-mdm-ui. 상태: 요구사항 정리/제품 정보 대기. MDM 설치 기능을 구현했다고 표시하지 않는다.

## 보존과 목표

시리얼 표시까지 포함한 v1은 main 및 v1.0.0-rc.1로 보존했다. 현재 기능·미해결 사항은 V1_BASELINE.md를 따른다. v2 작업은 별도 feature 브랜치에서 진행하고 v1 운영 Pi에는 자동 반영하지 않는다.

사용자 목표는 Office 설치 자체보다 기관의 MDM 관리 프로그램을 PC에 설치하는 것이다. MDM 앱을 최초 확장 대상으로 삼아 관리자 UI의 모듈 등록·검사·공개, 클라이언트 UI의 앱 선택과 진행/결과 확인을 설계한다. 기존 진단/복구 기획을 폐기하지 않는다.

## 다음 구현 범위 제안

1. MDM 제품과 정식 원본, 지원 Windows/아키텍처, 무인 설치·반환 코드·재부팅·필수 의존성·탐지 조건을 확인한다.
2. 앱 규약에 탐지/설치/검증과 의존성·패키지 버전·진행/오류 보고를 정의한다. 설치 완료와 MDM 서버 등록/관리 연결 완료를 별도 상태로 둔다. 등록 확인 방식이 없으면 등록됨을 추정하지 않는다.
3. 관리자 UI는 앱 이름/버전·패키지·검사 결과·공개 상태를 관리한다. 비밀 등록값은 별도 제한 저장소로 관리하고 일반 클라이언트 목록·공개 ZIP·로그에 넣지 않는다. 설치 파일이나 임의 스크립트를 업로드하는 것만으로 즉시 SYSTEM 실행하지 않는다.
4. 클라이언트는 공개된 호환 앱을 선택하고 서버는 선택 앱과 패키지 버전을 작업에 고정한다. MDM을 기본 필수로 둘지, Office보다 먼저 설치할지, 등록 실패 시 다른 앱을 중단할지는 사용자와 확정한다.
5. 처음에는 모의 모듈로 UI→선택 작업→버전 고정 배포→결과 반영을 검증한다. 이후 전용 Windows 시험 PC에서 MDM 설치·이미 설치됨·설치 실패·등록 실패·재부팅을 검증한다. 운영 PC의 MDM 제거/재등록은 임의로 수행하지 않는다.

MVC: Model은 앱/패키지/작업·보고 상태, Controller는 등록/검사/공개·요청·권한, View는 관리자 앱 관리와 클라이언트 선택 화면을 맡는다. PowerShell 실행기는 규약을 따르며 기존 에이전트와의 프로토콜 버전을 확인한다. 현재 Office/한컴 고정 보고를 MDM까지 확장할 앱별 상태 모델이 필요하다.

## 제품 정보 대기

사용자 전달(2026-10-16): 대상 설치 파일명은 `ArgosMDMSetup_v1.1.7_야탑`이며 중·고등학교 기기 관리 용도로 사용한다. 버전은 파일명 기준 1.1.7로 추정하며 파일 메타데이터로 검증하지 않았다. `야탑`의 의미나 기관별 등록값 내장 여부는 미확인이다. 현재 Tools에서 해당 이름의 원본을 찾지 못했다.

- 설치 파일 확장자(EXE/MSI), 실제 원본 경로 및 검증된 버전.
- 공식 무인 설치 명령과 탐지/설치 후 확인 방법.
- 등록 서버/기관 코드/인증서 등 필요 여부(실제 비밀값은 채팅으로 받지 않음).
- MDM이 Windows 업데이트/재부팅·네트워크 정책을 변경하는지, 완료 판정 방식.

제품 정보 없이 특정 설치 인자나 등록 성공 조건을 만들지 않는다. 현재 요청은 v2 착수이며 기관 MDM 등록이나 외부 서버 변경을 실행하는 승인이 아니다.

병렬 다운로드 지연·이어받기·재부팅 복구·PC별 모니터링은 V2_PLAN.md의 후보와 함께 범위를 조정한다. 제품별 보고 불일치와 실패 후 재요청 문제는 별도 미해결 사항으로 유지한다.
