# 멀티 서버 확장 검토

2026-10-22 사용자 질문에 대한 구조 검토다. 운영 중인 서버나 배포 설정을 변경하지 않았다. 동시 PC 수·증설 효과를 측정한 결과도 아니다.

## 현재 확인한 구조

- FastAPI 서버가 작업·상태 API와 설치 파일 전달을 담당한다. SQLite에 PC/작업/진행 데이터를 저장한다.
- AdminSessions는 프로세스 메모리에 세션을 보관한다. 서버나 worker를 단순 복제하면 로그인 상태가 공유되지 않는다.
- v1 media 다운로드는 요청별 임시 ZIP을 만들고 응답 후 삭제한다. v2 앱 패키지는 서버 데이터 디렉터리의 해시 기반 파일을 사용한다. 두 경로를 혼동하지 않는다.
- SQLite 트랜잭션으로 단일 DB의 작업 claim을 처리한다. 서로 다른 서버에 DB를 각각 복사하면 작업·PC 상태가 갈라지므로 그대로 수평 확장하는 구성이 아니다.

## 먼저 나눌 역할

관리 서버는 Pi 한 대에서 PC 등록·인증·작업·결과를 관리하고, 별도 노트북/서버는 설치 원본 전송을 담당하는 구성을 1차 후보로 둔다. 이전 다운로드 지연 보고에 맞춘 제안이며 성능 개선을 입증한 결과는 아니다.

관리 서버가 승인된 PC/작업에 파일 경로를 안내하고 에이전트가 해당 배포 서버로 받는다. 배포 서버는 권한/만료/패키지 해시를 검증해야 한다. 현재 v1 ZIP에는 제품 키도 포함될 수 있으므로 원본 디렉터리를 공개 정적 파일 서버로 전환하지 않는다. 캐시 가능한 공통 설치 원본과 비밀 설정 전달을 분리하는 설계가 필요하다.

사전에 패키지를 생성·버전 고정하고 파일 해시로 일관성을 확인한다. 에이전트의 캐시·재사용·이어받기와 서버별 다운로드 동시 수를 검토한다. v1/v2의 기존 전달/키 처리 동작을 각각 회귀 검증한다.

## 관리 서버까지 여러 대로 늘릴 때

여러 API 서버 앞에 요청 분배 장치를 두고 작업/진행·PC 등록 정보를 같은 저장소에서 관리한다. 필요에 따라 PostgreSQL 같은 서버형 DB로 이행하고 로그인 세션을 공유한다. 기존 SQLite 파일을 네트워크 공유 폴더에 두는 것을 기본 해법으로 삼지 않는다.

작업 수신은 원자적으로 한 주체가 가져가도록 하고, 작업 ID/멱등 처리/임대·중단 확인을 설계한다. 응답이 끊겼다는 이유로 Office 제거·설치를 다른 서버가 즉시 다시 실행해서는 안 된다. 결과 재전송과 설치 재실행을 분리한다. 파일 서버와 API 서버가 같은 패키지 버전을 가리키는지 확인한다.

Redis나 별도 메시지 큐는 필요할 때 도입한다. 멀티 서버라는 이유만으로 모든 구성요소를 한 번에 추가하지 않는다. 관리 서버 두 대도 DB·요청 분배·전원 등이 단일 장애 지점이면 자동으로 고가용성이 되지 않는다. 파일 배포만 분리하는 1차 구성 역시 관리 서버 장애를 해결하지 않는다.

## 성능과 운영 확인

1. 동일 원본·PC 조건에서 1대/2대/추가 대수의 다운로드 속도, 서버/클라이언트 CPU·디스크, 관리자 응답 지연을 측정한다.
2. 내부 유선망과 현재 외부 접속 경로를 비교하고 전체 공유 회선 한계를 구분한다. 파일 서버가 늘어도 같은 Wi-Fi/상위 회선 대역폭이 자동 증가하지 않는다.
3. 인증된 파일 전송·변조/손상·서버 단절·만료·중복 작업·진행 보고를 테스트한다.
4. 실제 환경의 목표 대수와 성능 결과로 API 복제나 추가 배포 노드를 결정한다. 임의의 동시접속 한계를 제시하지 않는다.

## 현재 제안 순서

측정 → 패키지 사전 생성/재사용 → 파일 배포 역할 분리 → 실제 동시 설치 비교 → 필요 시 관리 API/DB 확장.

서버를 여러 개 띄우는 것과 클라이언트 설치 병렬 실행은 별개다. 프로그램 설치 자체의 CPU 작업은 이미 각 Windows PC가 수행한다. 단순 웹 접속 수보다 설치 원본의 전송량·진행 보고 빈도·DB 쓰기 경쟁이 설계 판단에 중요하다.
