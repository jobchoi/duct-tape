# v1 재검증과 v2 착수 계획

갱신: 2026-10-14. 상태: 기획 초안. 실제 현장 테스트 결과는 미확정.

## 현재 기준선

- 최신 현장 로그에서 VC++ x86 건너뛰기, 한컴 MSI 종료 코드 0, 전체 설치 단계 완료를 확인했다. 앱 실행·인증 성공까지 검증한 것은 아니다.
- 이후 에이전트 종료 코드 오판과 UTF8 출력을 수정하고 Windows 실제 자식 프로세스 및 모의 설치 테스트를 통과했다. 해당 수정 적용 후 관리자 요청부터 클라이언트 실행·서버 완료 표시까지의 현장 검증은 아직 수행하지 않았다.
- 실패한 PC에서 관리자 셋업 시작 버튼이 반응하지 않는 현상은 미해결/미재현이다. 초기화로 증상이 사라져도 해결된 것으로 판정하지 않는다.
- 사용자 답변: 클라이언트는 Windows 재설치로 초기화한다. 서버 구축 방향은 Pi 4 → Pi 5이며 Pi 5를 목표로 계획한다. 병렬 대수/폐쇄망 작업은 수행하되 후순위로 둔다. 전환 전 WSL 검증 유지 여부와 이전 시점은 미확정이다.

## 다음 작업 순서

1. 기존 실패 작업 ID·시간·화면 상태와 필요한 로그를 비밀값 제거 후 보존한다. 서버 등록/로컬 파일을 지우기 전에 진행 중 설치가 없음을 확인한다. Windows 재설치로 바뀐 PC 식별값과 이전 등록의 관계도 기록한다.
2. 현재 코드 커밋과 테스트 PC Windows 버전, 다운로드 ZIP 일시를 기록한다. HTTPS 기본 주소가 포함된 최신 전체 ZIP으로 등록한다. Windows 재설치 후 Tailscale 경로로 접속하면 클라이언트 Tailscale도 다시 설치/연결한다. 이전 서버 등록은 작업 종료와 이력 보존 후 정리하고 새 PC 식별값으로 등록·승인한다.
3. 아래 v1 시험을 실행하고 서버·클라이언트 동일 작업 ID로 대조한다. 재현된 오류는 fix 브랜치에서 수정·회귀 검증한다.
4. 검증이 끝나면 운영 브랜치 main으로 검토된 v1을 반영하고 v1.0.0 태그를 붙인다. 검증 전 보존이 필요하면 v1.0.0-rc.1을 사용한다. 현재 문서 작업에서는 태그·main 머지·배포를 수행하지 않는다.
5. v1 운영 worktree와 v2 개발 worktree를 분리하고 v2 기능 규약/화면 흐름을 확정한다. develop에서 기능 브랜치로 구현한다.

## v1 현장 검증표

| 시험 | 기대 결과 | 현재 결과 |
| --- | --- | --- |
| 초기화 PC의 에이전트 등록/승인 | 연결 PC 1건, heartbeat 정상 | 미검증 |
| 관리자 PC 선택 후 셋업 시작 | 요청 응답과 작업 ID 표시, 클라이언트 실행 | 미검증 |
| 설치 완료/종료 0 | 동일 작업이 서버 succeeded, 마지막 AGENT_RESULT=0 | 최신 수정 후 미검증 |
| 클라이언트 선택/요청 | 자기 PC에만 작업 등록 및 실행 | 최신 수정 후 미검증 |
| 한글 작업 로그 | UTF8 조회 시 한글 정상, 키 비노출 | 실제 자식 프로세스 테스트 통과, 현장 미검증 |
| 설치 후 확인 | Office/한컴 실행·버전·재부팅·인증 상태 별도 기록 | 미검증 |
| 실패 후 다시 요청 | 버튼 반응/작업 생성 또는 구체적인 차단 이유 | 미해결 |
| 작업 중 중복 요청 | PC당 활성 작업 하나, 기존 작업 유지 | 현장 미검증 |
| 에이전트 재시작/연결 단절 | 중복 설치 없이 기존 상태 확인·정리 | 현장 미검증 |

실패 시험은 시험 PC의 복구 가능한 조건 또는 모의 설치기로 수행한다. 운영 매체/키를 훼손해 오류를 만들지 않는다. 특정 실패만으로 전체 Office 제거를 반복하지 않는다.

### 실패 후 버튼 무반응 조사

UI 비활성 조건과 선택 PC 유지 → 클릭 핸들러/브라우저 오류 → 네트워크 요청 유무·응답 → 서버 인증/매체/활성 작업 검사 → 클라이언트 ActiveJob.json 및 결과 전송 상태 순으로 확인한다.
failed/interrupted/offline을 구분하고, 실패 작업은 상태를 확인한 뒤 새 요청 가능해야 한다. 실행/중단 확인이 필요한 작업은 이유를 표시한다. 버튼 클릭 시 무반응으로 끝내지 않는다. 새 PC 정상 시험과 기존 실패 PC 시험을 별도로 통과해야 한다.

## v1 운영·v2 개발 분리

이 저장소에는 main이 있으므로 master를 새로 만들지 않고 main을 운영 기준으로 사용한다. 태그는 코드만 보존하므로 실제 매체·키·환경 설정·DB의 보관/복구 절차가 별도로 필요하다.

| 항목 | v1 운영 | v2 개발 |
| --- | --- | --- |
| 체크아웃 | main 또는 검증된 v1 태그 worktree | develop 및 feature worktree |
| 서버 | 기존 운영 포트/주소 | 별도 포트/주소 |
| DB/로그/임시 파일 | 운영 전용 | 시험 전용 |
| 에이전트 | 운영 서버에 등록 | 전용 시험 PC 또는 서버 전환을 통제한 PC |

새 worktree에는 Git 제외 파일과 Python 가상환경이 자동 복제되지 않는다. 환경별로 준비한다. 운영 DB의 개발 공유는 금지한다. 매체는 읽기 전용 공통 원본 사용을 검토하되 개발 변경이 운영에 반영되지 않게 버전을 고정한다. 한 PC의 SYSTEM 예약 작업과 ProgramData 경로는 현재 하나이므로 v1/v2 에이전트를 동시에 설치하는 구성은 지원한다고 가정하지 않는다.

## v2 범위와 구조

기존 V2_PLAN의 진단·복구·제거·병렬·기관망 방향을 유지하고 관리자 앱 등록/클라이언트 선택 설치 UI를 추가한다.

- 관리자 흐름: 앱 추가 → 메타데이터/패키지 등록 → 규약·매체 검사 → 초안 보관 → 공개/비활성. 실패 사유를 UI에 표시한다.
- 클라이언트 흐름: 공개된 호환 앱 목록 → 선택 → 설치 요청 → 앱별 진행/결과 → 실패 조치. 임의 명령 입력 UI는 제공하지 않는다.
- 최소 규약 초안: schema_version, 앱 ID/버전, 지원 OS/아키텍처, 탐지/설치/설치 후 검증 진입점, 의존성, 허용 종료 코드, 재부팅·진행/오류 코드. 제거는 별도 선택 기능/정책으로 정의한다.
- MVC: Model은 카탈로그/패키지 버전·작업 선택 목록과 상태, Controller는 등록/검사/공개/요청 및 권한 검증, View는 관리자 폼·목록과 클라이언트 선택 화면. PowerShell 공통 실행기는 규약을 해석한다.
- 앱 추가마다 에이전트를 수동 재설치하지 않도록 승인된 버전의 실행 모듈 패키지 전달/무결성 검사/클라이언트 규약 호환 검사를 설계한다. 기존 에이전트는 지원 범위가 다르므로 최초 v2 업그레이드 절차가 필요하다.
- 관리자 업로드는 클라이언트 SYSTEM 코드 실행으로 이어지므로 관리자 권한·허용 패키지 구조·경로 탈출 방지·해시/승인 이력을 설계한다. 일반 사용자는 모듈을 업로드/변경하지 않는다. 키는 별도 제한 저장소에 두고 등록 UI에는 설정 여부만 표시한다.
- 작업에는 선택 앱과 실행 패키지 버전을 고정한다. 등록 내용을 수정해 진행 중 작업이 다른 코드로 바뀌지 않게 한다. 실패 시 전체 설치를 재실행하지 않고 탐지/검증 후 앱별 재시도한다.

순서: v1 현장 검증/재요청 수정 → UI 흐름·규약 확정 → Office/한컴 공통 규약 적용 → 관리자 등록·공개 UI → 클라이언트 선택 설치 → 진단/복구 수용 시험 → 캐시/병렬/기관망 실장 시험.

## 미확정 질문

- 확정: Windows 재설치 후 재검증, Pi 4 → Pi 5 서버 구축 방향, 병렬/폐쇄망은 후순위.
- 추가 확인: Pi 5 준비 상태, RAM/SSD, 서버 전환 시점, v1 현장 시험을 현재 WSL에서 먼저 할지 여부.
- 목표 대수와 폐쇄망 세부 요구는 해당 후속 단계 착수 때 확정한다.
- 앱 업로드 방식과 Office 제거 대상/Project·Visio 보존은 UI 규약 확정 때 추가 협의한다.
