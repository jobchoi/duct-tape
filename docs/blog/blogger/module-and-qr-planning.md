# DuctTape 개발 일지 — QR 도구를 붙이기 전에 기능의 경계를 정리했다

기존에 사용하던 QR 유틸리티를 DuctTape 관리자 화면에서도 이용하고 싶었다. 파일을 옮겨 소스를 확인하니 두 도구 모두 명단으로 QR 라벨 PDF를 만들었지만, QR 내용과 출력 순서는 달랐다. 한쪽은 연도·이름·시리얼을 넣었고 다른 쪽은 시리얼만 넣었다.

그대로 화면만 붙이기보다 기본 기능을 먼저 작게 잡기로 했다. 입력한 값으로 QR을 만들고 미리보기와 이미지 다운로드를 제공하는 구성을 제안했다. 명단 업로드와 라벨 PDF는 후속 기능으로 구분했다. 이번에는 계획을 정리했으며 웹 QR 생성 기능을 구현한 것은 아니다.

## 시리얼을 다시 입력할 필요가 있을까

현재 DuctTape에는 Windows BIOS에서 시리얼을 읽고 서버에 보고하는 코드가 있다. 관리자 목록도 해당 보고값을 표시한다. 그래서 PC를 선택하면 그 시리얼을 QR 화면에 채우고 이름만 수기로 입력하는 방향을 정리했다.

다만 신규 등록만으로 시리얼을 즉시 받는다고 보장할 수는 없었다. 기존 수집 코드는 셋업 단계와 연결되어 있고 한컴 키 확인도 함께 수행한다. 설치와 무관하게 QR을 쓰려면 정보 수집을 분리할 필요가 있는지 확인해야 한다. 보고가 없으면 확인 전으로 표시하고, 오래되거나 잘못된 값은 사용자가 확인할 수 있게 하는 방향이다.

## OS가 달라도 같은 기능을 쓸 수 있을까

C에서 OS별 SDK를 참조하듯 이 프로젝트도 OS별 API를 이용할 수 있는지 검토했다. 핵심은 어디에서 실행하느냐였다. Windows 기기의 정보는 Windows 에이전트가 수집하고 라즈베리 서버는 공통 형식의 결과를 받는다. Windows 전용 SDK를 Linux 서버에서 그대로 실행하는 구조로 생각하지 않기로 했다.

기능이 늘어날 때 이용자가 블록을 고르듯 켜고 끄는 구조도 요구사항으로 남겼다. 관리자가 허용한 기능을 이용자가 선택하되, 화면을 숨기는 것뿐 아니라 서버에서도 비활성 기능의 요청을 막아야 한다. 기능을 끄는 일이 진행 중인 설치를 중단하거나 설치된 프로그램을 제거하는 일과 같지는 않다.

## 아직은 연결 준비 단계다

이번 작업은 코드 경로 확인과 요구사항 문서화였다. QR 연계와 기능 토글을 실행해 본 결과가 아니다. Blogger 연동도 Google Cloud 프로젝트 생성 단계까지 진행 중이라 글은 로컬 초안으로 남겼다. 실제 구현과 테스트가 끝나면 그 결과를 별도로 기록할 예정이다.
