# 클라이언트에 Tailscale을 설치하지 않고 라즈베리 서버에 접속할 수 있을까?

DuctTape 서버를 WSL에서 사용하다가 Raspberry Pi 5에 올렸다. 처음에는 클라이언트 PC에도 Tailscale을 설치해 서버에 접속했다.

그런데 실제 작업할 PC가 늘어나면 접속을 위해 매번 Tailscale까지 준비해야 하는지 궁금해졌다.

**클라이언트에서는 브라우저로 주소만 열고, 라즈베리 서버에 접속할 수 없을까?**

## 1. 웹 서버와 접속 경로를 구분했다

처음에는 ‘Tailscale로 서버를 운영한다’고 생각하기 쉬웠다. 실제 구성은 역할이 나뉘어 있었다.

Raspberry Pi의 Docker 컨테이너에서 DuctTape 웹 서버를 실행한다. Tailscale은 그 서버에 접속하는 경로를 제공한다. Windows 프로그램을 설치하는 작업은 각 클라이언트 PC의 에이전트가 실행한다.

```text
클라이언트 브라우저
        ↓
서버에 접속하는 경로
        ↓
Raspberry Pi의 DuctTape 웹 서버
```

따라서 외부 접속 설정을 하기 전에 서버 자체가 응답하는지부터 확인했다.

```bash
curl -f http://127.0.0.1:8000/api/config
```

이 요청이 실패했을 때는 접속 주소보다 웹 서버 기동부터 확인해야 했다. 실제 배포 초기에 8000번 포트로 연결되지 않는 상황이 있었고, 이후 컨테이너를 올린 뒤 정상 응답을 확인했다.

## 2. Serve와 Funnel은 접속 대상이 달랐다

기존 Serve 상태에는 tailnet only라는 표시가 있었다. 여기서 tailnet은 Tailscale로 연결한 사설 네트워크다. Serve는 그 네트워크 안에서 서비스를 공유하는 기능이다.

반면 Funnel은 로컬 서비스를 공개 인터넷에서 접근할 수 있도록 연결한다. 그래서 클라이언트에 Tailscale을 설치하지 않고 접속하려는 이번 목적에는 Funnel을 사용했다. 이 구분은 [Tailscale Serve 공식 문서](https://tailscale.com/docs/features/tailscale-serve)에서도 확인했다.

| 방식 | 접속 범위 |
| --- | --- |
| Serve | Tailscale 네트워크 안에서 공유 |
| Funnel | 공개 인터넷에서 접속하도록 연결 |

Funnel의 주소를 안다고 애플리케이션 사용 권한까지 생기는 것은 아니다. DuctTape의 관리자 인증과 PC 승인은 서버에서 별도로 처리한다.

## 3. 로컬 서버를 공개 HTTPS 주소에 연결했다

라즈베리에서 사용한 명령은 다음과 같았다.

```bash
sudo tailscale funnel --bg --https=443 http://127.0.0.1:8000
tailscale funnel status
```

이 명령은 외부 접속을 활성화한다. 여기서는 당시 실행한 명령을 기록한 것이며, 공개할 서비스를 확인하고 사용하는 설정이다.

출력에는 Available on the internet과 Funnel on이 표시됐고, 공개 HTTPS 주소가 로컬의 8000번 포트로 연결되는 것을 확인했다.

```text
공개 HTTPS 주소
        ↓
Tailscale Funnel
        ↓
라즈베리의 127.0.0.1:8000
        ↓
DuctTape 웹 서버
```

이후 해당 주소로 클라이언트 웹 화면이 열리는 것도 확인했다.

다만 브라우저에서 페이지를 여는 것과 Office를 설치하는 것은 별개다. Tailscale이 없는 PC에서도 웹페이지에 접속할 수 있지만, DuctTape의 설치 작업을 실행하려면 Windows 에이전트가 필요하다.

## 4. 그런데 다음에는 일부 기기에서 주소를 찾지 못했다

연결이 한 번 됐다고 이후 상태까지 항상 같았던 것은 아니다.

나중에는 라즈베리와 작업용 데스크톱에서 페이지가 열리는데, 모바일과 다른 탭북에서는 주소를 찾지 못하는 상황이 있었다. 서버 API는 정상 응답했고 Funnel 상태도 켜져 있었다.

처음에는 이 두 결과만 보면 외부 접속도 정상이라고 생각하기 쉬웠다. 하지만 내부에서 접속되는 것과 Tailscale이 없는 기기에서 공개 주소가 열리는 것은 다른 확인이었다.

Tailscale이 연결된 PC에서는 도메인이 Tailscale 주소로 조회됐지만, 공개 DNS 조회에서는 도메인을 찾지 못한다는 응답을 확인했다.

문제 범위를 다음처럼 나누게 됐다.

```text
로컬 API가 응답하는가?
        ↓
Funnel 설정이 켜져 있는가?
        ↓
외부에서 도메인을 조회할 수 있는가?
        ↓
실제로 HTTPS 요청이 서버까지 도착하는가?
```

이후 망을 바꾸지 않은 상태에서 외부 기기의 접속이 다시 되는 것을 확인했다. 다만 정확히 어떤 변화로 복구됐는지는 확정하지 못했다.

그래서 이 일을 ‘전원을 켜면 DNS가 늦게 등록되는 문제를 해결했다’고 정리하지는 않았다. 당시 확인한 것은 로컬 서버와 Funnel 표시가 정상이더라도 공개 DNS와 실제 외부 접속을 따로 확인해야 한다는 점이었다.

## 5. 웹 접속이 된다고 파일 전송까지 빠른 것은 아니었다

이후 설치 원본 다운로드가 느린 상황도 있었다. 웹 화면 접속과 대용량 파일 전송은 같은 조건으로 판단하기 어려웠다.

[Tailscale Funnel 공식 문서](https://tailscale.com/docs/features/tailscale-funnel)에는 조정할 수 없는 대역폭 제한이 안내돼 있다. 하지만 그 제한이 당시 다운로드 지연의 원인이었다고 확인한 것은 아니다. 네트워크와 클라이언트 등 다른 조건도 비교해야 한다.

이번 기록에서는 공개 HTTPS 접속 경로를 연결하고, 외부에서 접속되지 않을 때 확인할 구간을 나눈 과정까지만 남긴다.

## 정리하며

클라이언트마다 Tailscale을 설치하지 않고 웹 화면에 접속하려는 목적에는 Funnel이 접속 경로를 제공했다.

웹 서버는 라즈베리에서 실행하고, Funnel은 그 서버로 들어오는 길을 연결한다. 실제 프로그램 설치는 Windows 클라이언트가 맡는다.

이 역할을 나누고 나니 ‘서버가 안 된다’는 말을 조금 더 구체적으로 확인할 수 있었다. 서버 실행, 공개 주소 조회, HTTPS 접속, 설치 파일 전송은 각각 확인해야 하는 단계였다.
