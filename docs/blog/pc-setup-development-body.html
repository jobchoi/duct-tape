여러 Windows PC의 환경을 구성하기 위해 사용하던 BAT와 PowerShell 설치 도구를 웹에서 관리하는 형태로 바꾸고 있다. 기존에는 공유폴더에 있는 실행 파일을 클라이언트 PC에서 실행해 Office와 한컴을 설치했다. 이를 서버에서 PC를 확인하고 셋업을 요청하는 방식으로 확장했다.

이 글은 2026년 10월 15일까지 진행한 개발과 현장 확인을 정리한 기록이다. Raspberry Pi의 서버 기동과 공개 HTTPS 접속은 확인했지만, Pi에서 요청한 작업이 초기화한 Windows PC에서 설치를 마치고 완료 보고까지 하는 전체 과정은 아직 재검증 전이다.

서버가 작업을 관리하고 설치는 Windows에서 실행한다

개발과 초기 서버 실행은 WSL에서 진행했다. 서버는 FastAPI와 SQLite를 사용하며, 관리자 화면과 클라이언트 화면을 분리했다. 서버 코드도 Model, Controller, View로 역할을 나눴다.

웹페이지에 접속하는 것만으로 Windows 프로그램을 설치할 수 있는 구조는 아니다. 클라이언트 PC에는 PowerShell 에이전트를 설치하고, 에이전트가 서버의 작업을 조회해 실행한다. 에이전트는 SYSTEM 계정의 예약 작업으로 실행한다.

관리자는 PC 연결을 승인하고 셋업을 요청한다. 실제 Office와 한컴 설치는 해당 Windows PC에서 실행된다. 서버는 작업과 진행 상황, 결과를 관리하고 설치 원본을 전달한다. 따라서 Raspberry Pi가 Windows 설치기를 직접 실행하는 것은 아니다.

기존 스크립트를 앱 단위로 정리했다

처음부터 설치 스크립트를 전부 새로 만들기보다 기존 모듈을 재사용했다. 현재 기본 순서는 기기 정보 수집, Office 상태 확인·제거·설치, 한컴 상태 확인·설치의 여섯 단계다.

앱 정의는 Config/Applications.json에 두고, 앱별 설치 원본 후보와 필수 파일, 키 파일 위치, 실행 모듈을 구분했다. Tools 폴더에 옮겨둔 기존 원본도 참고하되 특정 폴더 하나에만 종속되지 않도록 원본을 찾는 로직을 분리했다.

이 작업은 나중에 다른 앱도 추가하려는 기반이다. 다만 관리자가 UI에서 새 모듈을 등록하고 클라이언트가 앱을 선택해 설치하는 기능은 아직 구현하지 않았다. 이 부분은 v2 계획에 포함했다.

진행률은 실제로 측정할 수 있는 값부터 표시했다

셋업 버튼을 누른 뒤 설치가 진행 중인지 알기 어려웠다. 단순한 회전 아이콘 대신 작업 단계와 진행 내역을 표시하는 기능을 추가했다.

다운로드는 받은 바이트 수, 압축 해제는 처리한 항목 수, 설치 모듈은 완료한 단계 수를 기준으로 보고한다. 클라이언트는 작업별 진행 이벤트를 기록하고 서버로 전달한다.

Office나 한컴 설치기 내부의 정확한 진행률까지 측정한 것은 아니다. 예를 들어 5/6은 여섯 모듈 중 다섯 개가 완료됐다는 뜻이지, 전체 설치 시간이 일정한 비율로 남았다는 뜻은 아니다.

한컴 설치 실패를 로그로 좁혀갔다

현장 테스트에서 한컴 설치 단계가 실패했다. 서버 로그만으로는 Windows 설치기의 상세 원인을 확인하기 어려워 클라이언트의 작업 출력 로그를 확인했다.

첫 실패 로그의 핵심은 다음 두 줄이었다.

PROCESS_EXIT: 1638
06 : INSTALL_PROCESS_FAILED

클라이언트에는 VC++ x86 런타임 14.50.35719가 설치되어 있었고, 한컴 원본에 포함된 VC_redist.x86.exe의 제품 버전은 14.29.30037.0이었다. 기존 로그에는 실행 대상 구분이 없어 당시 실패한 실행 파일을 확정하지는 못했지만, 선행 런타임 설치의 버전 충돌 가능성을 확인할 수 있었다.

이에 원본의 버전과 설치된 v14 x86 런타임 버전을 비교해, 같은 버전이거나 더 최신인 호환 런타임이 등록돼 있으면 설치를 건너뛰도록 수정했다. 1638을 무조건 성공으로 바꾸지는 않았다. 충돌 코드가 나와도 호환 버전을 다시 확인한 경우에만 다음 단계로 진행한다.

수정 후 전달받은 현장 로그에서는 런타임 건너뛰기, 한컴 MSI 설치 시작, 종료 코드 0, 한컴 설치 완료까지 확인했다. 다만 설치기의 성공 반환과 실제 앱 실행·정품 인증 확인은 구분해야 한다.

설치가 끝났는데 실패로 보이는 문제도 있었다

한컴 설치 완료 로그가 있는데도 작업 상태는 실패로 표시됐다. 이 과정에서 Windows PowerShell 5.1의 출력 리다이렉트 방식으로 실행한 자식 프로세스의 종료 코드가 빈 값으로 읽히는 현상을 별도로 재현했다.

프로세스 시작 직후 핸들을 유지하도록 수정하고, 실제 Windows 자식 프로세스로 0, 1, 3010 종료 코드가 보존되는지 확인했다. 이 테스트는 실제 설치기를 실행한 테스트가 아니다. 또한 과거 현장 작업의 서버 저장 종료 코드를 확인한 것은 아니므로 당시 실패 표시의 원인과 완전히 동일하다고 단정하지는 않는다.

추가로 출력이 한글 깨짐으로 보이는 문제를 다뤘다. 에이전트와 자식 스크립트의 콘솔 출력을 UTF-8로 통일하고 한글이 로그 파일에 보존되는지 검증했다. 에이전트의 최종 상태와 종료 코드도 AGENT_RESULT로 남기도록 했다.

로그는 문제를 좁히는 데 도움이 됐지만 모든 장애를 기록한다고 보장하지는 않는다. 강제 종료나 로그 저장 자체의 실패, 설치기 내부 상세 진단은 추가 보완이 필요하다.

Raspberry Pi 5에 Docker로 서버를 올렸다

이후 Raspberry Pi 5에 프로젝트를 배포했다. 기존 Nginx 홈페이지와 File Browser는 유지하고, duct-tape는 별도 Python 컨테이너로 실행했다.

Compose 파일은 저장소보다 한 단계 위에 두었다. 프로젝트 디렉토리를 빌드 경로로 지정하고 DB, 설치 원본, 임시 ZIP, 관리자 업로드 저장 위치는 컨테이너 외부 디렉토리로 분리했다.

Pi에서는 이미지 빌드와 컨테이너 시작이 완료됐고 healthy 상태를 확인했다. API 요청도 정상 응답했다.

curl -f http://127.0.0.1:8000/api/config

이때 서버 응답의 auth_mode는 secure였지만 media.ready는 false였다. 서버가 실행되지 않은 것이 아니라 설치 원본과 제품키가 준비되지 않은 상태였다.

이 과정에서 Git과 실제 배포 데이터의 차이를 다시 확인했다. git pull로 받는 것은 추적 중인 코드다. Git에서 제외한 Office·한컴 원본, 라이선스 키와 환경 설정은 별도로 옮겨야 한다. Linux에서는 OfficeKey.txt 같은 파일명의 대소문자도 맞아야 한다.

Tailscale Funnel로 공개 HTTPS 접속을 연결했다

초기에는 클라이언트에도 Tailscale을 설치해 접속했다. Pi에서는 Tailscale Funnel을 사용해 공개 HTTPS 주소를 서버의 localhost:8000으로 연결했다.

sudo tailscale funnel --bg --https=443 http://127.0.0.1:8000
tailscale funnel status

Pi에서 Available on the internet과 Funnel on 출력을 확인했고, 해당 주소로 클라이언트 웹 화면이 열리는 것도 확인했다. Funnel은 Tailscale이 없는 클라이언트에도 접속 경로를 제공한다. 하지만 이것이 DuctTape 에이전트 없이 Windows 프로그램을 설치한다는 뜻은 아니다.

공개 HTTPS 접속과 제품 설치 성공도 서로 다른 검증 항목이다. 현재는 Pi 서버 기동과 웹 접속까지 확인했으며, 설치 원본 준비와 초기화 PC를 이용한 전체 흐름 검증은 이어서 진행해야 한다.

다음 작업은 기능 확장보다 검증부터

현재 남은 현상 중 하나는 실패한 PC에 관리자 화면에서 셋업을 다시 요청했을 때 반응하지 않는 문제다. 초기화한 PC에서 정상 실행되는지만 볼 것이 아니라, 실패 후 다시 요청할 수 있는지도 따로 확인해야 한다.

다음 검증은 Windows 재설치 후 에이전트 등록, 관리자 승인, 서버 요청, 클라이언트 실행, 동일 작업의 완료 보고 순서로 진행할 계획이다. 앱 실행과 인증도 별도로 확인한다.

v1을 안정적으로 보존한 뒤에는 관리자 화면에서 앱 모듈을 등록·검사·공개하고, 클라이언트 화면에서 앱을 선택해 설치하는 흐름을 v2로 확장할 예정이다. 이를 위해 탐지·설치·검증·종료 코드·재부팅·진행 보고의 모듈 규약부터 정리하려 한다. 병렬 설치 규모 확대와 폐쇄망 지원은 후순위다.

이번 작업에서는 설치 스크립트 자체만큼이나 작업 결과를 정확히 구분하고 기록하는 과정이 필요했다. 설치기 종료, 실제 설치 상태, 앱 실행과 인증, 서버의 완료 표시는 각각 확인해야 하는 단계였다.
