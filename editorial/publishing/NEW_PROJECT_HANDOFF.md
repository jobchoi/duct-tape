# 여러 프로젝트에서 재사용할 블로그 도구 — 새 프로젝트 시작 문서

작성일: 2026-10-23
상태: 기존 구현 인수인계와 새 프로젝트 설계 제안. 별도 저장소 생성이나 UI 구현을 완료한 문서는 아니다.

이 파일을 새 프로젝트에 복사해 기획·코드 리뷰의 출발점으로 사용한다. 기존 대화 전체를 복사하지 않아도 목적·구현 범위·남은 작업을 이해할 수 있도록 작성했다.

## 개발·운영 환경을 포함한 초기 기획

WSL 개발, Windows 브라우저 확인, 여분 Raspberry Pi 시험 배포와 기존 서버에 함께 운영할 때의 격리 기준은 [초기 기획서](INITIAL_PROJECT_PLAN.md)에 정리했다. 새 프로젝트에는 이 문서와 초기 기획서를 함께 복사한다. 아직 보드·접속 방식이 확정되지 않았으며 Pi 배포가 끝난 상태는 아니다.

## 1. 목적과 프로젝트 경계

DuctTape의 PC 설치 자동화와 블로그 편집·업로드를 분리한다. 블로그 도구는 DuctTape뿐 아니라 다른 프로젝트의 원고도 받아 미리보기·검토·플랫폼별 업로드/내보내기를 처리한다.

DuctTape는 PC 등록·설치·진행 보고를 담당한다. 블로그 도구가 설치 기능이나 운영 DB에 직접 의존하지 않도록 한다. QTP는 편집·학습 원칙이며 블로그 도구의 실행 코드나 제품 기능과 구분한다.

처음에는 독립 CLI와 공통 라이브러리로 분리하고, 같은 기능을 호출하는 UI를 후속 추가한다. 여러 프로젝트가 원격으로 이용할 필요가 확인되면 API 서비스를 검토한다. 처음부터 여러 서버·메시지 큐·범용 플러그인 시스템을 도입하지 않는다.

## 2. 사용자 운영 방식

| 대상 | 글의 목적 | 작성 기준 |
| --- | --- | --- |
| Blogger | 개발·탐구 일지 | 질문 → 확인 과정 → 시행착오/선택 → 코드 근거 → 검증·남은 질문 |
| 티스토리 | 작업 지시·사용 매뉴얼 | 적용 조건 → 준비 → 실행 → 확인 → 오류 대응 |
| 네이버 등 | 추후 결정 | 독자·공식 지원 기능을 확인한 뒤 추가 |

가볍고 구체적인 문장으로 쓰되 기록에 없는 경험·감정·오류·성과를 만들지 않는다. ‘설정’, ‘설치기’ 같은 말은 문맥상 무엇인지 알 수 있게 구체화한다. 코드 작성·모의 테스트·브라우저 테스트·실제 기기 확인·운영 배포를 구분한다. 한 글에 핵심 질문을 두되 모든 글의 분량/절 수를 강제로 맞추지 않는다.

### 구현·검증한 범위

- Markdown 제목/본문을 분리해 HTML 미리보기를 생성한다. 허용 태그·속성·링크 스킴으로 정리한다.
- 공식 OAuth 라이브러리의 데스크톱/PKCE·loopback 흐름으로 계정을 연결하고 토큰을 로컬에 보관한다.
- 대상 Blogger 블로그와 작성자/관리자 접근을 확인한다.
- Blogger에 isDraft=true로만 업로드한다. 일반 CLI에 공개·삭제·원격 글 수정 명령은 없다.
- 로컬 SQLite에 업로드 상태를 기록하고 중복 요청을 막는다. 불확실한 네트워크 결과는 자동 POST 재시도 대신 원격 확인으로 연결한다.
- 재연결은 제목/HTML 해시로 확인하며 이전 기술 라벨도 호환한다. 새 글의 기본 라벨은 P-DuctTape·개발일지로 되어 있다.
- 기록상 오프라인 테스트 14개가 통과했다. 실제 Google 인증·Blogger 초안 업로드·원격 제목/HTML/DRAFT 일치·중복 방지를 확인했다.
- 기존 글의 본문/라벨 수정은 사용자 명시 요청으로 별도 API 작업을 수행했다. 이를 범용 CLI 수정 기능으로 오해하지 않는다.

### 아직 없는 기능

- 웹 UI, 여러 플랫폼 공통 인터페이스, 네이버 연결, 범용 티스토리 업로드.
- AI 자동 집필·리뷰 오케스트레이션, 예약 공개, 여러 사용자/기관 권한 관리.
- 여러 PC가 공유하는 중앙 게시 기록과 동시 편집 충돌 처리.
- Windows 네이티브 설치 전체 과정과 Pi ARM64 설치의 현장 검증.

## 4. 분리하면서 먼저 제거할 의존성

현재 CLI는 DuctTape 저장소 루트, docs/blog/blogger 입력 경로, 특정 Blogger URL, 기본 라벨, 인증 디렉터리 이름에 묶여 있다. 그대로 복사하면 다른 프로젝트용 도구가 되는 것은 아니다.

새 프로젝트에서는 대상 블로그·허용 원고 경로·출력 경로·기본 라벨·상태 저장 위치를 설정으로 옮긴다. 고정 경로를 없애더라도 서버가 임의 파일을 읽는 기능으로 확장하지 않는다. 입력 허용 범위와 파일 크기 검사를 유지한다.

프로젝트별 원고 ID를 구분한다. 예를 들어 여러 저장소에 draft.md가 있어도 같은 글로 취급하지 않도록 `project_id + article_id + target_id`를 식별에 사용하고, 제목/본문 해시는 원고 버전 확인에 사용한다. 파일 경로만으로 원격 글을 식별하지 않는다.

## 5. 권장 구조

```text
publishing-tool/
├── pyproject.toml
├── src/publishing_tool/
│   ├── core/          # 원고·검토 상태·게시 이력·공통 규칙
│   ├── rendering/     # Markdown/HTML 변환·미리보기
│   ├── providers/     # 플랫폼별 인증·지원 기능·업로드
│   │   ├── blogger.py
│   │   ├── tistory.py
│   │   └── naver.py
│   ├── storage/       # 게시 기록 저장소
│   ├── cli/           # 명령어 진입점
│   └── web/           # 후속 UI/API, 공통 로직 재사용
├── tests/
└── docs/
```

파일명과 구조는 제안이다. 미지원 플랫폼에 빈 업로드 기능을 만들어 실제 지원처럼 표시하지 않는다.

## 6. 플랫폼별 지원 기능

공통 도구는 플랫폼이 지원하는 기능을 확인하고 실행한다. 초안 업로드, 기존 글 수정, 라벨, 예약, HTML/Markdown 내보내기 등을 개별 기능으로 구분한다.

- Blogger: 기존 초안 업로드 경로를 먼저 이식한다.
- 티스토리: 기존 확인 기록상 공식 Open API가 종료됐다. 착수 시 최신 공식 지원을 재확인하고 우선 파일 내보내기를 제공한다.
- 네이버: 아직 공식 연동 방식과 지원 범위를 확인하지 않았다. 구현 착수 시 공식 문서·정책·인증을 확인한다.
- 브라우저 자동화는 공식 API와 다른 방식이다. 세션 보관·화면 변경·인증·오류 복구를 별도로 평가하고 지원 여부를 단정하지 않는다.

지원하지 않는 작업은 UI에서 이유를 표시하거나 내보내기로 연결한다. 실패한 업로드를 성공처럼 처리하지 않는다.

## 7. 다른 프로젝트의 이용 방식

```text
DuctTape 작업 기록 ──→ 검토할 원고/메타데이터 ──→ 블로그 도구
다른 프로젝트 기록 ─→ 검토할 원고/메타데이터 ──→ 같은 블로그 도구
```

호출 프로젝트는 project_id·article_id·원고·게시 대상·라벨을 전달한다. 블로그 도구는 대상별 인증과 게시 기록을 관리하고 상태/게시 ID/검토 필요 사유를 반환한다. 호출 프로젝트에 인증 토큰을 배포하지 않는다.

초기에는 CLI로 호출한다. 아래는 인터페이스 제안이며 현재 실행 가능한 명령이 아니다.

```text
publish-tool preview --project example --article office-key --source draft.md
publish-tool upload-draft --target personal-blog --project example --article office-key
```

나중에 UI와 API를 붙여도 원고 변환·검증·게시 상태 로직을 중복 구현하지 않는다. DuctTape 화면에서 접근할 필요가 있으면 별도 서비스 링크/탭으로 연결할 수 있다. 그 이유만으로 두 서비스의 관리자 세션·DB를 공유하지 않는다.

## 8. UI 최소 범위와 인증

연결 상태 → 원고 선택 → 일지/매뉴얼 구분 → 편집·미리보기 → 라벨 → 검토 확인 → 초안 업로드 → 결과·오류·중복 확인 순서를 제안한다.

원고 수정 후에는 이전 검토 승인을 그대로 사용하지 않는다. 공개는 작성자가 승인한 원고 버전으로만 처리한다. 초기 UI에서는 초안 업로드까지만 제공하는 것을 우선한다.

기존 데스크톱 OAuth와 웹 서버 콜백 방식은 구분한다. 서버 UI에서 여러 사용자의 Google 연결을 제공한다면 웹 OAuth 클라이언트·리디렉션·세션·요청 위조 방지·사용자별 토큰 접근 범위를 새로 설계한다. 현재 데스크톱 JSON을 웹 서비스 인증 설계로 그대로 대체하지 않는다.

## 9. 인증·자료·상태 보관

- 인증 JSON·토큰·실제 키·기관/개인 정보·로그 원본은 Git에 넣지 않는다.
- 현재 인증/게시 기록은 원본 개발 환경의 사용자 전용 디렉터리에 있으며 새 저장소로 자동 복사되지 않는다.
- 필요하면 인증을 다시 진행하거나 보호된 방식으로 이전한다. 현재 Windows 스크립트는 ACL을 자동 구성하지 않는다.
- 새 PC에 게시 기록 없이 같은 글을 다시 올리면 중복될 수 있다. 우선 하나의 업로드 담당 환경을 사용하고 이후 중앙 기록을 설계한다.
- 원격에서 작성자가 수정한 글은 로컬 원고로 무조건 덮어쓰지 않는다. 원격 버전/변경 여부를 확인하고 명시적 수정 요청과 연결한다.
- AI에 제공할 자료를 선택한다. 원고 전체·Git diff·설정·로그를 자동으로 외부 AI에 보내지 않는다.

## 10. 새 프로젝트 시작 순서

1. 원본 코드·테스트·문서를 검토하고 가져올 범위를 정한다. 기능을 이식하기 전에 현재 제약과 실패 경로를 확인한다.
2. DuctTape 고정 경로·블로그 URL·라벨을 설정으로 분리한다.
3. 기존 오프라인 테스트를 이식해 원고 변환·권한·초안 전용·중복/타임아웃·재연결을 검증한다.
4. Blogger 한 곳에서 초안 1편 업로드와 원격 저장 내용을 확인한다. 기존 실제 글을 새 테스트 자료로 반복 업로드하지 않는다.
5. 기존 글 수동 편집·토큰 만료·동시 요청·중복 파일명·원고 변경을 추가 테스트한다.
6. 최소 UI를 구현하고 인증/입력/미리보기·실패 복구를 코드 리뷰한다.
7. 티스토리·네이버의 실제 지원을 확인해 하나씩 연결하거나 내보내기를 제공한다.
8. 구현과 검증이 끝난 과정을 Blogger 일지·티스토리 매뉴얼로 나눠 기록한다.

플랫폼별 인증 설정을 모두 먼저 요구하지 않는다. API 연결 전에도 로컬 변환·미리보기·모의 테스트·내보내기를 진행할 수 있게 한다.

## 11. 새 채팅에 전달할 시작 요청

> 블로그 편집·초안 업로드 도구를 독립 프로젝트로 시작하려고 합니다. 이 문서와 가져온 기존 코드/테스트를 먼저 검토해 주세요. DuctTape 전용 경로·블로그·라벨 설정을 분리하고, Blogger 초안 업로드 기능을 먼저 유지·검증한 뒤 UI와 다른 플랫폼을 순차적으로 확장해 주세요. 실제 지원이 확인되지 않은 플랫폼 연동은 가능하다고 가정하지 마세요. 인증 정보는 저장소 밖에서 관리하고, 기존 원격 글의 수동 편집과 중복 업로드를 보호해 주세요. 작업 기록과 테스트 결과를 남기되 QTP 헌장·제품 설계·실제 검증 결과를 구분해 주세요. 공개 게시 전에는 작성자가 원고를 확인하도록 해주세요.

## 12. 인수인계 제외 항목

이 파일만으로 기존 계정 권한·인증 토큰·게시 기록·실행 환경이 이전되지는 않는다. 새 프로젝트를 생성하거나 자료를 복사한 사실, 실제 API 연결·업로드 성공은 해당 작업 후 별도로 기록한다.
