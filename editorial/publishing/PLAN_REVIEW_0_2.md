# 초기 기획 0.2 검토 기록

작성일: 2026-10-23

> 이전 검토 이력이다. 사용자 선택으로 서버형으로 변경했으며 현재 기준은 [기획 0.3](https://github.com/jobchoi/toyproject-HowToEasy/blob/develop/INITIAL_PROJECT_PLAN.md)이다.

일반 사용자용 로컬 설치형을 우선하는 제안을 채택한다. 개발 환경은 사용자 요청에 따라 WSL로 확정한다. 최종 사용자 앱의 지원 OS와 설치 형식은 아직 정하지 않았다. WSL 개발이 Windows 전용 배포를 의미하지 않는다.

## 채택한 방향

- 공통 로직과 플랫폼 어댑터를 CLI·로컬 UI가 함께 사용한다.
- 계정 인증 정보는 각 사용자의 실행 환경에 보관한다. 중앙 서버가 여러 사용자의 토큰을 수집하는 구조는 후속 범위다.
- 플랫폼별 지원 기능 선언·연결 점검·오류 분류·HTML 내보내기를 제공한다.
- Raspberry Pi는 개인 백업·선택적 상시 실행 용도로 검토한다.

## 보완한 내용

1. 로컬형도 OAuth 인증이 필요하다. 중앙 서비스 로그인은 초기 범위에서 제외하지만, Google 앱 검증 여부는 요청 권한·공개 범위·예외 조건에 따라 확인해야 한다. 데스크톱 앱이라는 이유만으로 면제되지 않는다.
2. localhost UI에도 요청 위조·미리보기 XSS·토큰 노출 방지가 필요하다. 플랫폼 비밀번호를 직접 수집하는 대신 공식 인증 흐름을 사용한다.
3. 업로드 응답이 끊겼다면 원격에서 이미 저장됐을 수 있다. 재업로드나 수동 붙여넣기 전에 원격 결과를 확인해 중복을 막는다.
4. 어댑터 독립 업데이트는 실행 코드 교체다. 초기에는 앱 전체 버전 업데이트를 우선하고, 독립 배포는 무결성·호환성·복구 절차를 마련한 뒤 도입한다.
5. 정기 점검은 모의 테스트와 읽기 전용 호출부터 시작한다. 실제 쓰기 시험은 별도로 허용한 테스트 블로그에서 초안·횟수·정리 정책을 정해 수행한다.
6. 일반 오류만으로 정책 변경을 확정하지 않는다. 원인 미상과 결과 불확실 상태를 유지한다. 제한된 재시도·토큰 갱신은 가능하지만 임의 코드 수정이나 AI의 무인 브라우저 조작을 기본 복구 방식으로 삼지 않는다.
7. 중앙 서버형 전환에는 사용자 격리·인증·운영 책임의 별도 설계가 필요하다. 공통 로직 재사용만으로 전환이 완료되지는 않는다.

## 다음 작업과 검증 경계

WSL에서 기존 코드 리뷰·공통 로직 분리·어댑터 모의 테스트·로컬 UI 개발을 진행할 수 있다. 설치 패키지·OS 키 저장소·업데이트 검증은 지원 OS 선정 후 실제 대상 환경에서 수행한다. 이번 변경은 문서 검토이며 코드 이식·앱 배포·외부 게시 결과가 아니다.

근거: [Google 데스크톱 OAuth 안내](https://developers.google.com/identity/protocols/oauth2/native-app), [민감한 권한의 앱 검증 안내](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification).
