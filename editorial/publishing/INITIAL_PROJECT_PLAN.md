# 블로그 편집·초안 업로드 도구 초기 기획서

작성일: 2026-10-23 · 버전: 기획 초안 0.1
프로젝트명: 미정
대상: 개인 운영자 1명이 여러 개발 프로젝트의 기록을 블로그별 원고로 정리하고 검토·업로드하는 독립 도구

이 문서는 사용자와 논의한 방향을 실행 가능한 개발 단계로 정리한 것이다. 새 프로젝트 생성·코드 이식·웹 UI 구현·Pi 배포를 완료한 문서는 아니다. 기존 구현의 출처와 가져올 파일은 [인수인계 문서](NEW_PROJECT_HANDOFF.md)를 함께 본다.

## 1. 해결할 문제

현재 작업은 원고 파일, CLI, Google 인증, Blogger 편집기를 오가야 한다. 작업 상태와 오류를 개발자가 터미널에서 확인하는 과정도 있다. 다른 프로젝트에서 사용하려면 DuctTape에 묶인 경로·블로그·라벨을 수정해야 한다.

목표는 어느 프로젝트의 기록이든 같은 도구로 가져와 원고를 검토하고, 지원되는 플랫폼에 초안으로 보내거나 편집기에 사용할 파일을 내보내는 것이다. 작성자가 지금 어느 단계인지, 무엇을 확인해야 하는지 알 수 있게 한다.

## 2. 제품 경계와 원칙

- PC 설치 자동화 DuctTape와 별도 저장소·서비스·데이터로 운영한다.
- QTP 헌장은 편집 기준으로 참조하며 제품 코드와 운영 절차를 대신하지 않는다.
- 사실 기반 원고를 우선한다. AI가 경험·감정·오류·검증 결과를 만들어 넣지 않는다.
- Blogger 일지는 질문과 확인 과정을, 티스토리 매뉴얼은 적용 조건과 실행 절차를 중심으로 구성한다.
- 초기 버전은 초안 업로드/내보내기까지다. 공개 발행은 블로그 편집기에서 작성자가 결정한다.
- 모든 플랫폼에서 같은 업로드 기능이 지원된다고 가정하지 않는다.

## 3. 개발·시험·운영 환경

| 환경 | 역할 | 확인할 사항 |
| --- | --- | --- |
| WSL | 주 개발, Python 테스트, Git, Docker 빌드/실행 | 소스는 WSL 파일시스템에 두고 실제 의존성을 분리 |
| Windows | 브라우저 UI·Google 로그인 확인, 필요 시 네이티브 CLI | 현재 PowerShell 진입점은 문법 확인까지이며 설치 전체는 별도 시험 |
| 여분 Raspberry Pi | 첫 Linux 서버 배포 및 상시 실행 시험 | 모델·RAM·OS·CPU 구조·저장장치·네트워크 사전 확인 |
| 기존 운영 Pi | 안정화 후 함께 운영할 수 있는 후보 | DuctTape 부하·포트·디스크·백업·복구 영향 비교 후 결정 |

WSL에서 개발해도 된다. 개발 편의 때문에 Windows 네이티브로 옮길 필요는 없다. WSL 개발 PC와 Pi의 CPU 구조는 같다고 가정하지 않는다. Python 패키지와 Docker 베이스 이미지의 대상 아키텍처 지원을 확인하고 실제 보드에서 설치·기동·업로드를 검증한다.

처음부터 기존 DuctTape 서버에 추가하지 않고 여분 보드에 시험 배포하는 것을 우선한다. 여분 보드 사양에 따라 기존 서버의 별도 컨테이너 시험으로 조정할 수 있다. 아직 사용 보드와 접속 방식은 확정하지 않았다.

## 4. 초기 범위

| 포함 | 후속 또는 제외 |
| --- | --- |
| 기존 Blogger CLI 이식·설정 분리 | AI 자동 집필·다중 AI 오케스트레이션 |
| 프로젝트/게시 대상 관리 | 여러 사용자·기관 운영 |
| Markdown 원고 편집·HTML 미리보기 | 자동 공개·예약 공개 |
| 원고 버전·검토 상태·라벨 확인 | 임의 플랫폼의 브라우저 자동 게시 |
| Blogger 연결·접근 확인·초안 업로드 | 다중 서버·고가용성 |
| 업로드 결과·중복·응답 유실 복구 | Pi에서 대형 AI 모델을 직접 구동 |
| HTML/Markdown 파일 내보내기 | 지원 미확인 플랫폼의 업로드 구현 약속 |

네이버는 지원 여부부터 공식 자료로 확인한다. 티스토리는 기존 확인 시점에 공식 글쓰기 API가 종료되어 내보내기를 우선하며 착수 시 지원 상태를 재확인한다. 초기 버전에서 두 플랫폼 계정 연결을 필수로 요구하지 않는다.

## 5. 사용자 흐름과 UI

1. **시작/연결 상태:** 준비 여부, 게시 대상, 인증 만료·권한 오류 확인.
2. **원고 선택:** 프로젝트와 원고를 고르거나 허용된 형식의 파일을 가져온다.
3. **원고 편집:** 원고 유형(일지/매뉴얼), 제목, 본문을 수정한다.
4. **미리보기·라벨:** 실제 업로드할 HTML과 분류 라벨을 확인한다.
5. **검토 확인:** 사실·검증 범위·민감 정보 확인을 현재 원고 버전에 연결한다.
6. **초안 업로드/내보내기:** 지원 기능에 맞는 동작만 제공한다.
7. **결과:** 게시 ID·초안 상태·확인 링크, 실패 이유, 안전한 다음 조치를 표시한다.

상태는 작성 중/검토 필요/업로드 대기/업로드 중/초안 저장 완료/실패/결과 확인 필요로 구분한다. 네트워크 응답 유실은 단순 실패가 아니라 결과 확인 필요로 처리한다. 텍스트·아이콘과 색상을 함께 사용하며 API 내부 진행률이 없으면 임의 퍼센트를 표시하지 않는다. 재시도는 기존 원격 글 확인과 구분한다.

CLI와 UI는 같은 공통 로직을 사용한다. 첫 UI에서 모든 설정을 한 화면에 펼치지 않고 작업 단계에 필요한 정보부터 보여준다.

## 6. 구조 제안

```text
입력 프로젝트들
  └─ 원고 + project_id/article_id + 게시 대상
        ↓
공통 원고/검토/상태 관리
  ├─ 변환·미리보기·라벨
  ├─ 업로드 기록·중복/충돌 확인
  └─ 플랫폼 연결 모듈
       ├─ Blogger: 인증·초안 업로드
       └─ 기타: 공식 지원 확인 후 연결/파일 내보내기
        ↑
      CLI / 웹 UI
```

Python 공통 라이브러리와 CLI를 먼저 유지하고 웹 계층을 덧붙이는 방식을 제안한다. 기존 경험을 활용해 FastAPI 기반 UI/API를 후보로 검토하되 프레임워크 선정 자체가 현재 확정 구현은 아니다. 초기 단일 서버의 게시 기록 저장소는 SQLite를 후보로 두고 필요가 확인될 때 서버형 DB를 검토한다.

플랫폼 연결 모듈은 초안 생성·수정·라벨·내보내기 등 지원 기능을 명시한다. 미지원 기능은 숨기거나 불가 사유를 표시한다. 여러 종류의 외부 응답을 공통 성공/실패/불확실 상태로 변환하되 세부 원인을 잃지 않는다.

## 7. 인증 설계

### CLI 단계

기존 데스크톱 OAuth와 PKCE·loopback 흐름을 유지한다. 브라우저 동의는 Windows/개발 PC에서 진행할 수 있다. WSL의 localhost 연결을 확인하고, 브라우저 없는 Pi는 SSH 터널 등 검증된 접속 방식을 사용한다. 다른 PC의 localhost가 Pi를 자동으로 가리킨다고 가정하지 않는다.

### 웹 단계

웹 화면의 Google 연결이 필요하면 웹 OAuth 클라이언트와 서버의 HTTPS 콜백을 설계한다. 데스크톱 인증 JSON을 웹 인증 설계로 그대로 대체하지 않는다. 접속 도메인과 공개/내부망 운영 방식을 확정한 뒤 리디렉션 URI를 등록한다.

Google 연결과 이 도구의 관리자 로그인은 별개다. 관리자 인증, 세션, 요청 위조 방지, 원고/토큰 접근 권한을 구현한다. 여러 서비스를 같은 호스트의 다른 포트로 운영할 때 포트만으로 쿠키가 격리된다고 가정하지 않는다. 서비스별 쿠키 이름·호스트·경로 정책을 확인한다.

인증 정보는 저장소·컨테이너 이미지·프런트엔드 응답에 넣지 않는다. 실행 시 보호된 파일/비밀 관리 방식으로 주입한다. 초기 한 사용자 구성이더라도 파일 권한을 제한하고 토큰을 로그에 남기지 않는다. Windows ACL과 Linux 컨테이너 UID/볼륨 권한은 각각 확인한다.

## 8. 원고·게시 이력과 안전한 재실행

- 식별: project_id + article_id + target_id. 파일명이나 제목이 같다는 이유로 같은 글로 보지 않는다.
- 버전: 제목·변환된 본문·라벨 등 검토 대상의 버전을 명확히 관리한다.
- 게시 기록: 요청 ID, 원고 버전, 대상, 진행 상태, 원격 게시 ID, 마지막 확인 결과를 저장한다.
- 원고 수정 후에는 이전 검토를 그대로 적용하지 않는다.
- 응답이 없으면 새 글을 바로 만들지 말고 원격 결과부터 확인한다.
- 사용자가 블로그 편집기에서 수정한 글은 로컬 원고로 덮어쓰지 않는다. 명시적 갱신 기능이 필요하면 원격 버전 확인과 충돌 처리를 설계한다.
- 복수 PC에서 각각 별도 게시 기록으로 같은 글을 업로드하는 문제를 막기 위해 초기 업로드 실행 환경을 하나로 정한다.

기존 CLI의 로컬 기록·본문 해시 비교는 출발점이다. 중앙 기록·원격 수동 편집·동시 실행까지 해결된 것으로 간주하지 않는다.

## 9. 배포·운영 구상

초기 시험은 여분 Pi에서 독립 컨테이너로 실행하는 구성을 제안한다. 서버 내부 포트·호스트 노출 포트·HTTPS 주소는 환경 확인 후 정한다. 운영 중인 DuctTape의 기존 Compose·Funnel 설정을 덮어쓰지 않는다.

```text
여분 Pi: 블로그 서비스
  ├─ 독립 애플리케이션
  ├─ 원고/게시 기록 저장소
  └─ 실행 시 주입하는 인증 정보

기존 Pi: DuctTape 운영 유지
```

같은 Pi에 함께 운영할 경우에도 컨테이너·포트·데이터·인증·로그·재시작 범위를 분리한다. 두 서비스를 함께 내리는 관리 명령을 기본값으로 삼지 않는다. CPU/RAM/저장 공간과 다운로드 부하를 측정해 판단한다. 장비가 하나이면 장애와 저장장치 문제의 영향은 공유한다.

관리자 UI는 HTTPS와 인증된 접근을 기본으로 설계하고 외부 공개 필요 여부를 먼저 결정한다. OAuth 콜백이 도달할 수 있어야 하며 임의 포트를 공개해 해결하지 않는다. 업로드에 외부 AI 연동이 필수인 구조로 만들지 않는다.

원고·게시 기록·인증 정보는 Git과 별도 백업 대상이다. 업데이트 전 백업, 이전 버전 실행, DB 변경 호환성과 복원 절차를 시험한다. 토큰만 보관하고 게시 기록을 분실하면 중복 방지가 유지되지 않을 수 있다.

## 10. 개발 단계와 완료 조건

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 0. 분리 준비 | 코드 리뷰, 추출 범위, 저장소·설정·식별 규약 | 고정 블로그/경로/라벨 의존성과 위험 목록 확인 |
| 1. CLI 이식 | 공통 기능/설정/테스트 이식 | 오프라인 테스트 및 별도 시험 글의 실제 초안 저장 확인 |
| 2. 최소 UI | 원고·미리보기·라벨·검토·결과 | 브라우저 전체 흐름과 실패 복구 테스트 통과 |
| 3. 웹 인증 | 관리자 로그인·웹 OAuth·토큰 보관 | 정상 연결·만료·거부·잘못된 콜백·권한 검사 확인 |
| 4. Pi 시험 | 실제 보드 설치·기동·재시작·업로드 | ARM 환경 테스트, 기존 서비스 영향 없음, 백업/복원 확인 |
| 5. 플랫폼 확장 | 공식 지원 확인, 추가 연결/내보내기 | 지원 기능별 계약 테스트와 가능한 실제 시험 |
| 6. 기록 | 코드 리뷰·문제·수정·검증을 일지/매뉴얼화 | 근거와 미검증 범위가 구분된 원고 |

2~3단계는 함께 설계한다. 인증 없는 UI를 외부에 공개하지 않는다. 소요 기간과 성능 목표는 보드·운영 방식·지원 플랫폼 범위가 정해진 뒤 산정한다.

## 11. 검증 계획

오프라인에서는 변환·허용 HTML·원고 크기/경로·인증 권한·중복 파일명·원고 변경·타임아웃·명확한 거절/불확실 결과·재연결을 검증한다. 기존 테스트를 그대로 옮기는 것뿐 아니라 새 구조에서 빠진 경계를 확인한다.

UI에서는 미리보기 XSS·외부 자료 로딩 정책·입력 제한·세션/요청 위조 방지·재검토·동시 클릭·원격 수동 편집 보존을 확인한다. 인증 파일 내용을 브라우저나 예외 응답에 노출하지 않는다.

Pi에서는 실제 의존성 설치·대상 아키텍처 이미지·재시작·네트워크 단절·토큰 갱신·디스크 공간·백업 복원을 확인한다. 실제 Blogger 시험은 전용 원고를 초안으로 올리고 상태·본문·라벨을 다시 읽는다. 기존 글을 실험마다 중복 생성하지 않는다.

## 12. 착수 시 확인할 항목

- 여분 보드 모델·RAM·OS/CPU 구조·저장장치.
- 내부망 전용인지, 다른 장소에서도 접속해야 하는지.
- 기존 서버와 함께 운영할 필요가 있는지, 여분 보드 시험이 가능한지.
- 첫 사용자는 본인 1명인지, 계정 공유 없이 추가 사용자가 필요한지.
- Blogger 외의 첫 확장 대상과 우선 기능: 업로드인가, 파일 내보내기인가.

미정이어도 WSL에서 코드 리뷰·CLI 분리·오프라인 테스트는 진행할 수 있다. 위 정보가 없는 상태에서 외부 공개·계정 이전·실제 Pi 배포까지 완료했다고 판단하지 않는다.
